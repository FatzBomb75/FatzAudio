# Engineering notes

Known issues and follow-up work that were found while doing something else and
kept out of that change so it stayed small. Add new entries at the top. When an
item is fixed, delete its entry in the same change and mention the PR there.

Each entry has a date, the area it touches, what's wrong or missing, and where it
was found (a PR, a review, or a thread).

| 2026-10-27 | Web streams | Connection reuse (audit step 4): a seek, a reconnect after a stall, or a reader that stops early, in the middle of a transfer, closes that connection on HTTP/1.1 (the rest of the body isn't read), so the next request makes a new TLS handshake. Only HTTP/2 (curl and URLSession when the server offers it) cancels just the stream. Reading the rest of a small remainder instead would keep the connection; not done. WinHTTP pools connections across session handles in the process (seen in CI: a one-shot request's connection was taken by the next stream), so on Windows the gain over the old code may be smaller than the Linux measurement, and WinHTTP doesn't retry a request on a pooled connection the server closed: `net_https_winhttp.c` retries once on `ERROR_WINHTTP_CONNECTION_ERROR` / `INVALID_SERVER_RESPONSE`. Android keeps no per-stream state: `HttpURLConnection` pools by itself, and a redirect's body is left unread there (the connection closes), unlike curl, WinHTTP and URLSession, which read up to 64 KB of it. No transport keeps cookies (WinHTTP and URLSession have theirs turned off, so that a kept session doesn't replay them): a server that sets a session cookie on its playlist and wants it back on the segments (ffmpeg's HLS demuxer passes them on) won't get it; a per-stream cookie jar in `fa_http_session` would. Measured only against `tools/test-https/serve.py` and a local delay relay: real CDNs, HTTP/2 servers and proxies are checked once Keith's player exists. | Audit step 4 thread |
