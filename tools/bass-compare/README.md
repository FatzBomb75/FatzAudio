# bass-compare

A black-box comparison of FatzAudio with BASS 2.4, the library it replaces. Both libraries decode the same test files, and every result is scored against what the file is known to contain. The report says, feature by feature, where FatzAudio matches BASS, where it is better and where it is worse.

BASS is only ever called through its documented public API: `bass_bench` loads `bass.dll` and its add-ons from a folder at run time, exactly as an app does. Nothing of BASS is in the repository, linked at build time, unpacked or inspected.

| Tool | What it does |
|---|---|
| `fa_bench` | FatzAudio's side, on decode-only streams through the public C API |
| `bass_bench` (Windows) | BASS's side: `BASS_StreamCreateFile` with `BASS_STREAM_DECODE \| BASS_SAMPLE_FLOAT`, add-ons loaded with `BASS_PluginLoad` |
| `loop_rec` | Records what reaches the sound card, for the playback measurements. It belongs to neither library (it opens its own capture device through miniaudio), so both are recorded by exactly the same code |
| `run.py` | Makes the test files, runs the tools, scores the results and writes `report.md` and `results.json`. Needs Python 3 with numpy and scipy, and an FFmpeg command line (`ffmpeg`) for encoding the test files |

## What it measures

| Area | Measured |
|---|---|
| Decoding | WAV (16, 24, float), FLAC (16, 24), MP3 (CBR with LAME header, VBR, no header), AAC (M4A, ADTS, MP4), AC-3 (stereo, 5.1, in MKV), E-AC-3 5.1, Opus (Ogg, WebM), Vorbis, WMA. Accuracy against FFmpeg's decode and against the original signal, where the audio starts, how many frames come out |
| Length | The length each library reports right after opening, and after a prescan |
| Speed and memory | Decode speed, time to open, time to the first audio, memory per stream; 16 streams at once |
| Seeking | Eight seeks per file, forwards and backwards: whether each lands on the frame asked for, with and without a prescan, and how long it takes |
| Loudness | FatzAudio's scan against EBU Tech 3341 cases and a BS.1770-4 reference meter; scan speed on long MP3 and video files against BASS just decoding them (BASS has no loudness meter) |
| Disc images | `.cue` + `.bin` tracks against the exact source audio (basscd reads drives only) |
| Tempo and pitch | [tempo-compare](../tempo-compare/README.md) with bass_fx, when its tools are passed |
| Playback (with `--rec`) | On the real output device: start latency, crossfade timing and shape, gapless joins. See [Playback on a real device](#playback-on-a-real-device) |

CD+G sync and web streams are left to the unit tests (see the report's last section).

FatzAudio runs without FFmpeg throughout. `--ffmpeg-dir` (Windows) or `--fa-ffmpeg` (Linux) only retries a file FatzAudio cannot open natively yet with an FFmpeg loaded at run time, and the report marks those rows **FFmpeg-assisted** (†): they stand in until FatzAudio's own decoder for that format lands.

All test signals are generated by `run.py` (synthesized drums, bass, chords and a lead, a quiet passage and a fade-out; 5.1 has different content in every channel), so there are no licensing questions.

## Windows

```bat
cmake -S . -B build
cmake --build build --config Release
pip install numpy scipy
python tools\bass-compare\run.py --fa build\bin\Release\fa_bench.exe ^
    --bass build\bin\Release\bass_bench.exe --bass-dir C:\development\nuget\fatzaudio\legacy ^
    --ffmpeg-dir C:\path\to\ffmpeg\bin --out bass-results
```

`ffmpeg.exe` must be on `PATH` (or pass `--ffmpeg`) to make the test files; that is the only thing the harness itself uses FFmpeg for. Optionally, `--ffmpeg-dir` is a folder with FFmpeg DLLs (`avcodec-*.dll`, `avutil-*.dll`): a file FatzAudio cannot open natively is then retried with them, and marked FFmpeg-assisted. Without it those rows say FatzAudio cannot open the file.

Add `--rec build\bin\Release\loop_rec.exe` to include the playback measurements (below).

Add `--fa-tempo build\bin\Release\fa_tempo_render.exe --bassfx build\bin\Release\bassfx_render.exe` to include the tempo and pitch comparison.

A full run takes a few minutes; `--runs` sets the speed runs per file (default 5, the best counts), `--long-minutes` the length of the scan-speed files (default 10), and `--only wav16,mp3-cbr` runs only those decode cases (and skips the long scan-speed files). The case names are in `make_inputs` in run.py.

## Linux, with Wine

Cross-build both tools for Windows with MinGW-w64 and run them under Wine, so both libraries run the same way. Optionally, a native Linux `fa_bench` retries any format FatzAudio cannot decode natively yet with the system FFmpeg (`--fa-ffmpeg`, rows marked FFmpeg-assisted †).

```sh
sudo apt-get install wine64 gcc-mingw-w64-x86-64 g++-mingw-w64-x86-64 ffmpeg python3-numpy python3-scipy
cat > mingw.cmake <<'EOF'
set(CMAKE_SYSTEM_NAME Windows)
set(CMAKE_C_COMPILER x86_64-w64-mingw32-gcc)
set(CMAKE_CXX_COMPILER x86_64-w64-mingw32-g++)
EOF
cmake -S . -B build-win -DCMAKE_TOOLCHAIN_FILE=mingw.cmake -DCMAKE_BUILD_TYPE=Release -DFA_BUILD_TESTS=OFF
cmake --build build-win -j
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j --target fa_bench fa_tempo_render
python3 tools/bass-compare/run.py --fa build-win/bin/fa_bench.exe --fa-wine \
    --fa-ffmpeg build/bin/fa_bench --bass build-win/bin/bass_bench.exe \
    --bass-dir /path/to/legacy --wine /usr/lib/wine/wine64 \
    --fa-tempo build/bin/fa_tempo_render --bassfx build-win/bin/bassfx_render.exe --out bass-results
```

## Playback on a real device

With `--rec`, both libraries also play through the default output device while `loop_rec` records what reaches it. Turn the volume down or plug in headphones: it plays a few clicks and tones for about a minute. `--device-only` runs just this part.

```bat
python tools\bass-compare\run.py --device-only --fa build\bin\Release\fa_bench.exe ^
    --bass build\bin\Release\bass_bench.exe --bass-dir C:\development\nuget\fatzaudio\legacy ^
    --rec build\bin\Release\loop_rec.exe --out device-results
```

| Test | What it measures |
|---|---|
| Start latency | A click started 20 times (`fa_stream_play`, `BASS_ChannelPlay`): time from the call to the sound, its spread, and the latency each library reports |
| Crossfade | A 2 s crossfade between two steady tones (`fa_crossfade`; BASS: `BASS_ChannelSlideAttribute` on both volumes): when each fade starts after the call, how far apart the two start, their length, how closely they follow the curve, and the loudness dip in the middle. Linear for both, and equal power for FatzAudio (BASS slides are linear only) |
| Gapless | A file queued after another (`fa_stream_set_next`; BASS: a `BASS_SYNC_END` sync that starts the second stream, with and without `BASS_SYNC_MIXTIME`): the gap or overlap at the join |

How it works: the players print the time of each call on the system's monotonic clock (`QueryPerformanceCounter`, `CLOCK_MONOTONIC`), and `loop_rec` stamps every block it records on the same clock, so each call lines up with the recorded audio. The two tones sit on the centres of analysis bins (468.75 and 703.125 Hz), so the level of each is followed separately every millisecond. The recorder's own capture delay is part of every latency figure, the same for both libraries, so the difference between them is exact and the absolute numbers are an upper bound.

What it records:

- **Windows** (default): the WASAPI loopback of the default output device, i.e. exactly what the system sends to the speakers. Nothing else should play meanwhile.
- `--capture <name>` records an input device whose name contains `<name>` instead: "Stereo Mix", a loopback cable, or a microphone near the speakers (that adds the acoustic path, the same for both). `loop_rec --list` prints the names.
- **Linux**: PulseAudio's monitor of the output, `--capture "Monitor of"`. Under Wine, run `loop_rec.exe` through Wine as well (`--rec-wine`), so that all three programs use Wine's clock (it is offset from the Linux one), and capture the monitor the same way:

```sh
python3 tools/bass-compare/run.py --device-only --fa build-win/bin/fa_bench.exe --fa-wine \
    --bass build-win/bin/bass_bench.exe --bass-dir /path/to/legacy --wine /usr/lib/wine/wine64 \
    --rec build-win/bin/loop_rec.exe --rec-wine --capture Monitor --out device-results
```

A recording where the two tones drop far below full level (the device lost audio) is taken again, up to three times; `attempts` in results.json says how many it took. Levels are measured relative to what was recorded, so the system volume does not matter. When a measurement fails, the report lists it with how much was recorded and how loud it was, and the recording is kept in `failed-recordings` in the output folder (16-bit WAV) for a look.

A machine without a sound card can use a PulseAudio null sink (`pulseaudio --start --load="module-null-sink sink_name=out"`); its timing is a virtual device's, not a real one's, so treat it as a check that everything runs.

## Reading the report

- The report opens with **where FatzAudio is worse than BASS**: every measurement where BASS won by more than the noise margin. Everything else is a tie or a FatzAudio win.
- Accuracy is signal-to-error in dB; 200 means bit exact. Against FFmpeg it shows the decoder's own accuracy; against the original it shows what the codec allows. Above about 80 dB a difference cannot be heard.
- Speed and memory under Wine are comparable between the two libraries (both are Windows code running the same way), but not with a native Windows run.
- Bold marks the better result where the gap is larger than the margin given above each table.

## Using the tools alone

```
fa_bench [--ffmpeg <dir>|system] decode <in> <out.f32|-> [--prescan]
fa_bench [--ffmpeg <dir>|system] seek <in> <out.f32> [--prescan] <frames> <frame> [<frame> ...]
fa_bench [--ffmpeg <dir>|system] multi <in> <streams>
fa_bench [--ffmpeg <dir>|system] loudness <in>
fa_bench [--ffmpeg <dir>|system] disc <image.cue> <track> <out.f32|->
fa_bench play-latency <click.wav> <trials> <gap ms>
fa_bench play-crossfade <a.wav> <b.wav> <fade ms> <start after ms> [linear|equal]
fa_bench play-gapless <a.wav> <b.wav>
bass_bench <bass folder> decode|seek|multi|play-latency|play-crossfade ...   (same arguments)
bass_bench <bass folder> play-gapless <a.wav> <b.wav> [mixtime|normal]
loop_rec <out.f32> <seconds> [--capture <name>]
loop_rec --list
```

Each prints one JSON line (format, reported length, frames, timings in ms, memory in KB; the play commands print the time of each call); audio is written as raw interleaved 32-bit float, `-` discards it. `loop_rec` prints `{"ready":...}` once audio is arriving, then, when done, the time stamp of every block it recorded.
